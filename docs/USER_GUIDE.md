# USER_GUIDE — 사용자 안내서

문서 버전 1.0 · 2026-10-15 · 전제: [INSTALLATION.md](INSTALLATION.md)대로 설치하고 `streamlit run src\proposal_agent\app.py`로 실행한 상태

화면은 좌측 사이드바에서 고른다. 모든 단계는 **승인 게이트**를 코드가 판정하며, 사람 승인이 필요한 곳에서는 검토 의견을 입력해야 다음으로 넘어간다. 에이전트가 실행되는 단계에는 API 키와 크레딧이 필요하고, 없으면 그 단계만 오류로 멈춘다(나머지 기능은 동작).

---

## 1. 공통: 시작 화면

- **새 프로젝트**: 이름, 모드(제안 단계 `proposal` / 구축 단계 `build`), 발주처(선택), 과제 시작일·종료일을 입력하고 생성한다. `Output\Project_<날짜>_<이름>\00_~13_` 폴더가 만들어진다.
- **열기**: 기존 프로젝트를 선택해 연다. 이후 모든 화면은 "현재 프로젝트"에 대해 동작한다.
- 상단 배너에 API 키 설정 여부가 표시된다.
- **입력 형식(단계 2)**: RFP 는 PDF·DOCX·TXT 외에 **PPTX**(슬라이드별 텍스트·표)와 **이미지(PNG·JPG, OCR)** 도 받는다. OCR 엔진이 없으면 이미지 추출은 실패로 기록된다(없는 텍스트를 만들지 않음). 문서 종류 **'회의록·인터뷰·질의응답'** 을 올리면 추출까지 되고 결정·조치 구조화는 단계 5 에서 제공된다. HWP 는 PDF 변환 후 업로드.
- **사업성 평가 화면(단계 2)**: 요구사항 기준선 승인 뒤 '평가 실행·갱신' 을 누르면 코드가 13개 항목을 판정하고 권고(제안)·근거·가정·비용 산정을 보여 준다. 예산·역할별 단가(프로젝트 설정) 가 없으면 수익성은 '산정 불가' 로 남는다. 항목별로 사용자 판정·메모를 넣어 재평가할 수 있고, '에이전트 검토 의견 받기'(API 키 필요) 는 의견만 덧붙인다. **참여 결정 기록** 은 결정 4종·근거·권한 확인으로 Decision(DEC) 에 남으며 권한 미확인이면 '제안' 상태다. 평가서는 `02_RFP_Analysis/사업성평가_vX.Y.md`.
- **요구사항 화면 '품질 검토' 패널(단계 2)**: 중복·수치 충돌·검증 불가 표현·구현 방안 불명확·RFP 근거 없음·업무 규칙 누락·비기능 누락·테스트 불가능한 수용 기준을 코드 규칙으로 찾아 검토 목록으로 보여 준다(QA-RFP-09 와 같은 규칙).
- **프로젝트 화면 '설정' 탭(단계 1)**: 사업 설명·일정 제약·예산·공수 상한·기존 시스템·기술 선택 모드(RFP 지정 준수/기존 유지/AI 추천/사용자 지정/혼합)·기술 스택·RFP 명시 기술·보안/개인정보·외부 솔루션·연계 시스템·산출물 종류/형식·역할별 단가·간접비율을 저장한다. RFP 가 기술을 명시한 사업에서 모드를 바꾸면 사유가 필수다. 단가가 없으면 사업성 평가·비용 산정은 '산정 불가' 로 남는다.
- **프로젝트 화면 '실행 계획' 탭(단계 1)**: 실행할 단계를 고르면 단계별 상태·실행 가능 여부·차단 사유(선행 단계 미완료·실행 중·API 키 없음)·진행률을 미리 보여 준다. '선택 단계 실행'(동기 또는 백그라운드), '실패한 단계만 재실행', '끊긴 작업 정리'(프로세스 종료로 '실행 중' 에 멈춘 작업을 실패로 정리), 백그라운드 작업 목록과 '중단 요청' 을 제공한다. 업로드·인력 기간·최종 확정은 각 화면에서 사람이 진행한다.

## 2. 제안 단계 (proposal)

### 2.1 프로젝트 화면 — 문서 등록
1. 문서 종류 `RFP`(필수, 1개)·`RFP 첨부`·`참고 그림(사진·일러스트)`(Phase 20, PNG/JPG, 추출 대상 아님)·`기타`를 고르고 파일을 올린 뒤 **등록**을 누른다. 지원 형식: DOCX, TXT/MD, PDF(텍스트·스캔). HWP/HWPX/DOC는 등록은 되지만 추출 단계에서 "지원하지 않음 + 변환 방법"으로 안내된다.
2. 원본은 `01_RFP_Original`에 그대로 보존된다. 같은 내용(해시 동일)은 거부되고, 같은 이름은 `_1`로 저장된다.
3. 단계 진행 표와 미해결 이슈가 같은 화면에 표시된다.

**제안서 템플릿(PPT) 등록 (선택, Phase 12)**: 문서 종류에서 `제안서 템플릿(PPT)`를 고르고 고객 양식 PPTX(세로 A4 제출용 또는 가로 발표용)를 올린다. 용도는 '자동(세로=제출용, 가로=발표용)' 또는 직접 지정한다. 템플릿은 텍스트 추출 대상이 아니며(Gate 0 무관) 산출물 화면의 **제안서 템플릿** 패널에서 코드가 읽은 용지·머리글 2단·리드 메시지·글꼴·장/절 구성·표 유형을 확인할 수 있다. 제안마다 양식이 다르므로 매 프로젝트에 다시 등록한다. 등록하지 않으면 코드 기본 양식(16:9)으로 만든다.

### 2.2 문서 추출 화면 (Gate 0)
1. **전체 추출** 또는 **미추출·실패 문서만 재처리**를 누른다. 텍스트 PDF는 pdfplumber, 스캔 PDF는 OCR(rapidocr, 한국어)로 읽는다.
2. 문서별 블록 수·추출 방식·신뢰도·검토 필요 블록이 표시된다. Gate 0은 코드가 평가한다. `NEEDS_HUMAN_REVIEW`이면 블록을 확인하고 검토 의견을 적은 뒤 **검토 후 통과**를 누른다. `FAIL`은 승인으로 통과시킬 수 없고 문서를 바꿔 재처리해야 한다.
3. **RFP 구조 프로파일**(화면 하단): 코드가 RFP의 절 구성(사업 개요·현황·범위·요구사항·작성요령·제출·평가·별첨), RFP 자체 요구사항 ID 체계(예: SFR-001, 접두사별 건수), 요구사항 목록(ID·명칭·페이지), 지정 제안서 목차, 평가 항목·배점, 제출 서류, 제거한 표 잡음(세로 병합 라벨) 수와 경고를 보여준다. 고객사마다 양식이 달라 인식은 휴리스틱이다. 절이나 ID가 잡히지 않으면 경고가 뜨며, 그 경우 문장 단위 추출만 된다(오류 아님).

### 2.3 요구사항 화면 (Gate 1)
1. **요구사항 추출(에이전트)** → 요구사항 초안이 ID(FR-/NFR-/CON-/EVA-/SUB-)와 원문 출처(문서·블록·인용)로 저장된다. RFP가 자체 ID(SFR-001 등)를 부여한 문서면 각 요구사항에 `RFP ID`가 함께 기록되고, 연결된 추출 요구사항이 하나도 없는 RFP ID는 경고(`rfp.uncovered_id`)로 남는다. 경고가 난 ID는 해당 절을 보고 **수동 추가**하거나 재추출한다.
2. **독립 검증(에이전트)** → 누락·중복·왜곡·출처·모순·범위를 별도 컨텍스트에서 검사해 지적 사항(findings)을 남긴다.
3. 목록에서 항목을 선택해 내용을 수정하거나, 수용 여부(수용/조건부 수용/미수용/검토 필요)를 정하거나, 검토 승인·반려, 삭제(상태 변경, 물리 삭제 아님)를 할 수 있다. **수동 추가**도 가능하며 ID는 코드가 발급한다. 편집 폼의 **구현 방안·구현 난이도(상/중/하)·검사 기준·검증 방법**은 요구사항 정의서의 구현 묶음 컬럼이 된다. 구현 방안을 직접 고치면 '사람 작성(user)'으로 표시되어 에이전트가 덮어쓰지 않는다. 난이도는 구축 단계 변경 요청의 공수·일정 영향 가중치(하 0.7 / 중 1.0 / 상 1.4)로 쓰인다.
4. 지적 사항을 **사람 확인 완료**로 해소한 뒤 **Gate 1 재평가**를 누른다. `NEEDS_HUMAN_REVIEW`면 의견을 적고 **검토 후 Gate 1 통과**. 이 게이트를 지나야 기술 조사·산출물 생성이 열린다.

### 2.4 에이전트·조사 화면
- **연결 점검**: 모델 호출 없이 SDK·MCP 연결 상태를 확인한다(비용 0).
- **RFP 분석 실행(에이전트)**: 사업 개요·범위·제약·평가·일정·예산·명시 솔루션·연계 대상을 정리한다 (`02_RFP_Analysis/rfp_analysis_vX.Y.json`).
- **기술 조사 실행(에이전트, 웹 검색)**: 조사 주제를 고른 뒤 실행하면 출처(URL·제품·버전·신뢰도)와 미확인 사항이 함께 저장된다. 결과는 사람 검토 항목이며, 출처 없는 주장은 "미확인"으로 표시된다. 각 조사 기록에 **사람 확인 완료**를 남길 수 있다.
- **구현 설계 작성(에이전트, 웹 검색)**(Phase 23): 요구사항 묶음마다 **실제 구현 방법**을 설계한다 — 구현 구조(구성 요소·계층·기술), 처리 절차(담당·처리·분기), 적용 기술과 선정 이유·검토한 대안·근거(열람한 URL·조사 ID, 확인/미확인), 데이터·인터페이스, 전제·위험. 아키텍처 설계 뒤에 실행하며, 결과는 제안서 '요구사항별 구현 방안' 소절의 구조 도식·절차 도식·적용 기술 표가 된다. 실행하지 않으면 묶음 소절은 정의서 구현방안 표와 기능 블록 도식만 싣고 QA-CON-13 이 검토를 요구한다.
- **구현 방안 작성(에이전트)**(Phase 14): 요구사항마다 정의서의 **구현방안(글머리 2~5줄, 제안서보다 짧게)·구현 난이도·난이도 근거·검증 방법·검사 기준**을 쓴다. 기술 조사·아키텍처 근거가 있는 내용만 구체화하고, 근거가 없으면 웹 검색으로 확인한 출처를 조사 기록으로 남기거나 "추가 조사 필요"로 보고한다. 에이전트가 빠뜨린 항목은 조사·구성 요소 데이터로 만든 규칙 초안이 `[자동 초안]` 표시로 들어가며(사람 확인 대상), 사람이 쓴 방안은 유지된다. 실행하지 않아도 산출물 생성 시 빈 항목은 규칙 초안으로 채워지고 QA-CON-09·QA-TECH-07이 확인을 요구한다. 평가 기준·제출 조건 요구사항은 대상이 아니다.

### 2.5 산출물 화면 (Gate 5)
1. 과제 기간을 확인·저장한다(UI 입력이 RFP의 "N개월"보다 우선). **제안서 템플릿** 패널에서 등록된 템플릿 프로파일과 RFP 지정 제안서 목차(장/절)를 확인한다.
1-0. **목차·전략 브리프 작성(에이전트) → Gate P 승인**(Phase 18): RFP 분석 후 곧바로 전체 제안서를 쓰지 않는다. '전략·목차 브리프 작성(에이전트)'을 누르면 RFP 분석 요약, 요구사항별 중요도·대응 방향, 제안서 목차 초안(RFP 지정 목차 보존), 주요 전략 3~5개와 차별화 근거, 핵심 기술·구현 방향, 예상 위험·대응, 제출용/발표용 구성 차이, 자료 부족·확인 필요 사항이 화면과 `07_Submission_Proposal_PPT/전략브리프_vX.Y.md`에 나온다. 검토 의견을 적고 **검토 후 Gate P 승인** 또는 **반려(수정 요청)** 를 누른다. 반려하면 의견이 다음 작성에 반영된다. 브리프 없이 승인할 수도 있으나(코드 기본 목차·데이터 기반 문안) 그 사실이 QA-RFP-08에 기록된다. Gate P 승인 전에는 '제안 문안 작성'과 '최종본 확정'이 막히고, '산출물 생성'은 시안으로만 만들어진다.
1-1. **제안 문안 작성(에이전트)**(Gate 1·**Gate P** 필요, **기술 조사 선행 필수**): 구현 가능한 내용만 쓰도록 기술 조사(웹 검색) 기록이 없으면 실행을 거부한다. 조사 결과는 관련 요구사항의 구현 방안을 "(근거: 조사 …)"로 채우고, 근거 조사가 없는 필수 기능 요구사항은 요약에 건수가 표시된다. 템플릿 관행·RFP 지정 목차·기준 데이터(요구사항 ID·RFP ID·WBS·인력)를 넣어 proposal_writer가 장·절·소절별 문안(리드 메시지·글머리·표·대응 요구사항 ID·※ 주석)을 작성한다. 실행하지 않으면 코드 기본 문안으로 생성한다.
2. **산출물 생성**: 아키텍처·WBS가 에이전트 결과로 있으면 그것을, 없으면 코드 기본값(검토 필요 표시)을 써서 구성도 3종·일정/공수 차트, 요구사항 정의서·추적표·WBS/간트·인력 투입계획(Excel 4종), 제출용·발표용 PPT를 만든다. 파일은 종류별 폴더에 `_vX.Y`로 저장된다. 제출용 PPT는 템플릿이 있으면 그 마스터·레이아웃 위에 **장 표지(로마숫자·장 제목·절 목록) → 절(N.) → 소절(N.M)** 구조로 만들고, 장·절 뼈대는 RFP 지정 목차 → 템플릿 샘플의 장·절 → 단일 장 순으로 정한다. RFP가 요구한 절에 채울 데이터가 없으면 비우지 않고 "RFP 작성방법 … / 사람 작성 필요" 자리표시 슬라이드를 넣는다. **도식은 모두 편집 가능한 도형·연결선·표**로 그린다(그림 삽입 없음): 구성도·일정(간트)·공수 막대·목표 카드·전략 카드·요구사항 KPI/2열 비교·위험 2열, 그리고 에이전트가 소절에 지정한 도식(카드·단계 흐름·호출 절차·2열 비교·데이터 흐름·화면 설계·핵심 수치·비교 표). PNG 구성도는 `10_Diagrams_Charts_Images`에 별도로 남는다. **발표용 PPT**는 표지 → 사업 필요성(카드) → CONTENTS → CHAPTER 구분(로마숫자·장 제목·절 목록) → 절마다 리드 문장 + 도식 + 요점 5개 이하 → 핵심 메시지 → 핵심 기술 순이며, 발표용 템플릿(가로)을 등록하면 그 양식(`NN/ 제목` 머리글, 큰따옴표 리드, 장 구분 레이아웃)을 쓴다. 목차 결정 기록(`07_Submission_Proposal_PPT/목차결정_vX.Y.json`)에 장 계획과 사용 템플릿이 남는다. **슬라이드 명세(Phase 19)**: 제안 문안의 소절마다 결론형 제목(`key_message`)이 리드 상자에, 목적·독자·앞뒤 연결이 발표자 노트에, 근거(`evidence`)가 하단 ※ 주석에 들어가고, 기술 소절은 '기술 상세' 카드와 '대안 비교(상용/공개/자체)' 표, 용어집은 부록 '용어 설명' 표가 된다. 생성 후 `슬라이드명세_제출용|발표용_vX.Y.json`(슬라이드별 제목·계획/실제 레이아웃·도식·근거·요구사항 ID)이 같은 폴더에 남고 산출물 화면의 '슬라이드 명세' 패널에서 볼 수 있다. 결론형 제목·근거가 없는 소절은 검토 항목으로 표시된다. 에이전트가 고를 수 있는 도식은 14종(책임 분담표·데이터 모델·운영 절차·보안 통제·계층 구성·**네이티브 차트** 추가). **요구사항 묶음별 구현 방안(Phase 22)**: '제안 시스템 주요 기능' 절 아래에 코드가 **요구사항 묶음**(제안 문안의 `requirement_groups`가 있으면 그대로, 없으면 RFP 고유번호가 같은 세부 요구 → 분류 순)마다 한 장을 만든다 — 결론형 제목, 요점(대응 요구사항·요약), '기능 구성' 블록 도식(사용자 → 기능 → 연계 대상), '요구사항별 구현 방안' 표(정의서 구현방안 **전문**·난이도·검증 방법/검사 기준), 넘치는 행은 (계속) 장, 전제·협의는 ※ 주석. 도식 소절은 **요점 → 도식 → 기술 상세(2열 표)** 를 한 장에 밴드(어두운 소제목 띠)로 배치하고, 한 장에 안 들어가면 표를 (계속) 장으로 나눈다. 카드·2열·띠는 내용에 맞춰 높이를 제한한다. **편집 가능 객체 강화(Phase 20)**: 역할별 공수·요구사항 통계(유형별 필수/선택)·제출용 일정(간트)은 PowerPoint **네이티브 차트**(데이터 시트에서 값·계열·색을 직접 수정)로, 화면 설계는 입력 필드·버튼·메뉴·탭·메시지·목록 표·차트 영역 **개별 컴포넌트**로 그리고 목업·카드·수치 카드·엔티티는 **그룹**(그룹 해제 가능)으로 묶는다. 발표용 일정 축은 자유 배치가 필요해 도형으로 남긴다. 프로젝트 화면에서 **참고 그림(사진·일러스트)** 문서 종류로 PNG/JPG를 올리면(그림 종류 태그·설명 입력) 제안 문안이 `picture`로 참조한 소절 뒤에, 참조되지 않은 그림은 제출용 부록 '참고 그림'에 태그 달린 그림으로 들어간다(QA-FILE-12 예외로 기록). 표·구조도·차트·화면은 여전히 이미지로 넣지 않는다.
2-1. **WBS·투입계획 양식(Phase 15)**: WBS 파일은 **WBS(상세)**(구분·개발 항목·수량·개발 조직·담당 역할·개발자·계획/실제 시작·종료일·진척율·진행 상태·공수·관계 + 오른쪽 주 단위 간트)와 **약식WBS(보고용)**(구분·단계·항목·시작일·종료일 + 간트, 첫 행 마일스톤) 시트를 한 파일에 담는다. 마일스톤(착수·착수보고·중간보고·완료보고·종료)은 planner 에이전트가 주지 않으면 코드 기본값이며 검토 메모가 남는다. '개발자'·'실제 시작/종료일'·'진척율'은 구축 단계에서 사람이 갱신한다. 투입계획 파일은 **투입계획**(수행 조직·역할·구성원·등급·월별 공수 MM·계·비고, 하단 월별 합계 행)과 **역할요약**(인원·단가·비용) 시트로 나뉘며, 구성원 이름은 planner의 `team`에 있을 때만 들어가고 없으면 `역할N` 자리표시로 표시된다.
3. **인력 단가 입력(선택)**: 역할별 단가를 넣고 다시 생성하면 역할요약에 비용 합계가 채워진다. 단가가 없으면 비용은 계산하지 않는다.
4. **QA 실행**: 통합 QA(독립 검증 53항목: RFP 적합성 9·기술 타당성 7·문서 간 일관성 13·파일 품질 14·편집 가능성 10; **단계 2**: QA-RFP-09 '요구사항 품질'(중복·충돌·검증 불가·누락 — 검토); **Phase 23**: QA-CON-13 '구현 설계 깊이 ↔ 제안서 반영'(묶음마다 구조 2·절차 3·적용 기술 1·데이터/인터페이스 1 이상이고 그 문구가 제출용 PPT 에 있는가 — 설계 없음·출처 미확인·설계에서 빠진 요구는 검토, 미달·미반영은 실패, 재생성으로 자동 수정); **Phase 22**: QA-CON-12 '정의서 구현방안 ↔ 제안서 반영'(수용된 기능·비기능 요구의 구현방안 줄이 제출용 PPT에 있는가 — 필수 기능 요구가 한 줄도 없으면 실패, 일부만 있으면 검토, 재생성으로 자동 수정); **Phase 21**: QA 실행 전에 '실제 렌더링·재열기 검증' 체크(이 PC에 PowerPoint가 있으면 기본 켬)와 'QA 범주'(비우면 전체, 내용/파일·디자인/편집 가능성을 나눠 실행 가능)를 고른다. QA-FILE-13 '페이지 제한'은 RFP에 쪽 수 제한 문구가 있을 때 제출용 본문 슬라이드 수를 대조하고, QA-FILE-14 '실제 렌더링·재열기'는 PowerPoint COM으로 두 덱을 열어 슬라이드마다 PNG(`11_QA_Validation_Reports/render/<덱 이름>/slide_NN.png`)를 내보내고 저장 왕복 후 재열기를 확인한다(PowerPoint가 없거나 꺼져 있으면 '미실행'으로 보고서에 남고 통과로 세지 않음). QA-EDIT-01~10 '편집 가능성'은 텍스트 상자·네이티브 표·도형/연결선·네이티브 차트·그룹 해제 가능·그림 태그·글꼴·발표자 노트·레이아웃·재열기 안정성을 객체 구조로 검사한다(발표용 소절 슬라이드에 노트가 없으면 코드가 '[발표 노트 초안]'을 채움); QA-CON-10 '제안 문안 추상 표현·근거 없는 수치'(과장 표현, 기준 데이터·근거에 없는 단위 수치 → 검토)와 QA-CON-11 '약어·전문 용어 설명'(용어집이나 괄호 풀이가 없는 영문 약어 → 검토)(Phase 19)와 QA-RFP-08 '목차·전략 승인(Gate P)'(승인 전이면 검토 필요, 반려면 실패)과 QA-CON-09 '요구사항 정의서 구현 방안·난이도'(수용된 구현 대상 요구마다 구현 방안·난이도·검사 기준이 있는가, 규칙 초안은 검토)와 QA-TECH-07 '기능 요구사항 구현 근거'(수용된 필수 기능 요구의 구현 방안·구현 가능 조사 연결)와 QA-FILE-12 '편집 가능성'(PPT에 태그 없는 그림, 즉 표·구조도·차트·목업을 이미지로 넣은 것이 있으면 실패; 사진·일러스트·장식·참고 이미지는 `photo/illustration/decoration/reference` 태그로 삽입하면 허용되고 보고서·manifest에 예외로 기록됨)이 추가됨; QA-RFP-07 'RFP 요구사항 ID 커버리지'는 RFP에 ID 체계가 있을 때만, QA-FILE-11 '제안서 템플릿 준수'(용지·머리글 위치·장 순서·글꼴)는 템플릿을 등록했을 때만 실행하며 QA-FILE-02 용지 검사도 템플릿 크기를 기준으로 한다)가 돌고, 재생성으로 고칠 수 있는 파일 문제는 설정 횟수(기본 2회) 안에서 자동 수정·재검증된다. 결과 표와 Gate 2·3·4·5 상태가 표시되고 보고서가 `11_QA_Validation_Reports\통합QA보고서_vX.Y.md`에 남는다.
5. **Gate 5 승인**: 필수 검증 실패(FAIL)가 없을 때만 승인할 수 있다. 검토 의견을 적고 **검토 후 승인**을 누른다.
6. **최종본 확정**: Gate 5 통과 후 누르면 최신 산출물이 `13_Final_Deliverables`로 복사된다(임시본은 원 폴더에 보존).

산출물의 "검토 필요/미정" 표기는 데이터가 확정되지 않았다는 뜻이다. 수용 여부·기술 스택·공수를 확정한 뒤 다시 생성하면 사라진다.

## 3. 구축 단계 (build)

### 3.1 구축: 기준 문서 화면
1. 요구사항 정의서·요구사항 추적표·WBS(필수)와 인력 투입계획·기타(선택) Excel을 올려 **등록**한다.
2. **구조 분석 실행**: 시트와 컬럼이 자동 매핑된다(표준 양식은 즉시, 다른 양식은 동의어·유사도로 제안). "확인 필요"로 표시된 컬럼은 열 번호를 지정하고 **이 문서의 매핑 확정**을 누른다. 필수 컬럼이 미확정이면 적재가 거부된다. 제목 행·묶음 머리글이 있는 고객 양식도 컬럼 머리글 행을 자동으로 찾고, '요구사항 해결 방안/구현내용'(구현방안)·'난이도'·'검사·판정 기준'·'대분류/중분류'·'고유번호'·'요구사항변경여부'·'검토 및 협의 내용'·'화면/보고서ID'·'단위/통합테스트케이스ID'·'완료여부' 같은 헤더를 인식한다. 표지·개정이력·요구사항목록(요약)·작성가이드 시트는 적재하지 않는다. WBS는 'WBS ID' 열이 없는 고객 양식(구분·항목·세부·수량·담당 + 주 단위 채움)도 받아들여 구분>단계>항목 계층으로 코드(1, 1.1, 1.1.1)를 발급하고 경고를 남긴다(날짜 없는 주 단위 채움은 읽지 않음). 월별 투입계획(구분·등급·월·계)은 같은 역할 행을 묶어 역할·등급·기준 MM으로 적재한다.
3. **기준 데이터 적재**: 요구사항(기존 ID 유지)·추적 링크·화면/테스트 ID·WBS·의존관계·역할이 적재되고 Revision v1.0 스냅샷이 `12_Revision_History`에 남는다. 적재 결과와 경고(중복 ID, 날짜 형식 등)가 표시된다.
4. 아래 표에서 현재 기준 요구사항을 조회한다.

### 3.2 구축: 변경 관리 화면
1. **변경 요청 등록**: 입력 방식을 고른다.
   - 자연어 입력: 여러 항목은 줄바꿈이나 번호로 구분한다.
   - 추가(버튼) / 수정·삭제(요구사항 선택): 대상 요구사항을 다중 선택한다.
   - 문서 업로드: DOCX/PDF/TXT에서 텍스트를 발췌해 요청문으로 쓴다.
   요청자·요청일·사유·제목을 적고 **등록 전 미리보기**로 확인한 뒤 등록한다.
2. **분석 실행**: 규칙 기반 의미 비교가 항목별로 `추가 / 수정 / 삭제 요청 / 변경 없음 / 모호`를 분류하고 근거·신뢰도·관련 ID를 보여 준다. "AI 의미 비교 사용"을 켜면 에이전트 의견이 덧붙는데, 규칙과 다르면 자동으로 결정하지 않고 "모호"로 낮춘다. 영향 분석(변경 전후 종료일, Task별 공수·일정, 역할별 MM, 인력 시나리오 1~6, 단가가 있으면 비용)이 함께 계산된다.
3. **후보별 결정**: 각 후보를 수락/거절하고, 필요하면 분류·대상 ID·내용·공수 확정값·담당 역할을 직접 입력한다(사용자 입력은 AI/규칙 추론과 구분되어 저장된다). "모호" 후보는 분류와 대상 ID를 지정해야 수락할 수 있다.
4. **승인·기준 반영·문서 재생성**: 미결정 후보가 없고 영향 분석 오류가 없을 때만 버튼이 켜진다. 승인하면 새 ID 발급(기존 ID 체계), 요구사항 이력·이전 버전 보존, 삭제는 상태 표시, 추적 링크 '재검토 필요', WBS·일정 갱신, Revision 생성, 그리고 `Requirements_Definition_YYYYMMDDHHMM.xlsx` 등 새 버전 파일이 만들어진다. 투입계획이 업로드된 경우에만 "인력 투입계획도 갱신"을 켤 수 있다.
   **반려**는 사유가 필수이며 기준 데이터를 바꾸지 않는다. 반영 중 오류가 나면 롤백되고 **반영 재시도** 버튼이 나타난다.
5. **변경 후 통합 QA 실행**: 변경 이력↔기준 데이터, 정의서↔추적표, WBS↔일정, 파일 품질을 검사한다.
6. 화면 하단의 **변경관리대장**과 Revision 이력(v1.0 → v2.0 → …)으로 모든 변경을 조회한다. 같은 내용은 재생성된 정의서의 `변경관리대장` 시트에도 들어 있다.

## 4. 자주 묻는 상황

| 상황 | 설명 |
|---|---|
| 버튼이 비활성 | 앞 게이트가 통과되지 않았다. 화면 상단의 게이트 상태와 사유를 확인한다 |
| `Credit balance is too low` | Anthropic 계정 크레딧 부족. 충전 전까지 에이전트 단계는 실행할 수 없다 |
| `ANTHROPIC_API_KEY` 없음 | `.env`에 키를 넣고 앱을 재시작한다 |
| 산출물에 "미정/검토 필요"가 많음 | 아키텍처·계획 에이전트를 실행하지 않았거나 수용 여부가 미확정. 확정 후 재생성 |
| 매핑 확인 필요 | 기준 문서의 헤더가 표준과 달라 열 번호를 직접 지정해야 한다 |
| 변경 승인 버튼이 꺼짐 | 미결정 후보, 모호 후보 수락, 영향 분석 오류(순환 의존 등)를 해결한다 |
| 파일이 `_1`로 저장됨 | 같은 이름이 이미 있어 보존 저장했다. 덮어쓰기는 하지 않는다 |
