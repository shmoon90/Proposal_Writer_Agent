# 제출용 제안서 샘플 분석 (2026-10-15)

분석 대상: 사용자가 제공한 **고객 실과제 제출용 제안서 샘플 3종**(저장소 밖, 커밋·공개 금지). 앞서 분석한 고객 제공 RFP 샘플에 대한 제안서의 일부다. 이 문서는 **서식·구조·작성 방식만** 기록하며 고객사명·사업명·제품명·원문 문장은 적지 않는다.

| 파일 | 용지 | 장 수 | 내용 |
|---|---|---|---|
| 제출용 Ⅰ장 파일 | A4 세로 21.6 × 30.3 cm | 28 | Ⅰ장(제안 개요): 1. 사업 이해도 · 2. 추진전략 · 3. 관리방법론 · 4. 개발방법론 |
| 제출용 Ⅲ장 파일 | A4 세로 21.6 × 30.3 cm | 10 | Ⅲ장(사업수행 부문): 1. 시스템 구성 방안 · 2. 제안 시스템 주요 기능 · 3. 시스템 특징 및 장점 · 4. 일정계획 |
| 세부 추진 일정 별지 | A3 가로 35.6 × 26.7 cm | 1 | 4.2 세부추진 일정계획 (간트 표 14×8) |

python-pptx로 슬라이드 크기·레이아웃·마스터 고정 요소·도형 좌표·글꼴·표 머리글을 읽어 정리했다. 발표용 제안서는 §4에서 다룬다.

## 1. 구조

- **장(Chapter) 단위 파일**: RFP가 지정한 제안서 목차(Ⅰ 제안개요 · Ⅱ 제안업체 일반 · Ⅲ 사업수행 부문 · Ⅳ 사업관리 부문 · Ⅴ 지원 부문)의 장마다 PPT 파일 1개. 장 안의 절(1. 2. 3. 4.)도 RFP의 "제안서 목차 및 작성방법" 표의 항목을 그대로 따른다.
- **장 표지**(장 표지 전용 레이아웃): 전면 배경 그림 + "CHAPTER" 라벨 + 로마숫자(36pt 흰색) + 장 제목(34~36pt, 진한 남색) + 그 장의 절 목록("1. … / 2. … / …").
- **본문 슬라이드**(장마다 본문 레이아웃 1개): 레이아웃에 장 이름·로마숫자·쪽번호 `Ⅰ - ‹#›`(하단 중앙)이 고정되어 있고, 마스터에 상단 띠(0~2.6 cm)·제안사 로고·하단 로고가 있다.
- **본문 머리글 2단**(모든 본문 슬라이드에서 좌표가 같음):
  - 1단 `top 3.7~3.8 cm, left 2.0, w 17.5, h 0.4` — "N. 절 제목" (굵은 고딕 10pt). 하위 절이 깊어지면 "3. 관리방법론 > 3.4 자원관리 방안"처럼 경로 표기.
  - 2단 `top 4.5~4.6 cm, left 2.0, w 15.3~17.5, h 0.6` — "N.M 소절 제목" (굵은 고딕 13pt). 같은 소절이 이어지면 "(계속)".
- **본문 영역**: 머리글 아래 약 5.3 cm부터 하단 로고 위 28.8 cm까지(좌 2.0, 폭 17.6 cm). 맨 아래 `※ …` 주석(9~10pt, top 27.5 cm 전후).

## 2. 작성 방식 (내용)

- **리드 메시지**: 소절 첫 슬라이드 상단에 요약 문장 1~2개. Ⅲ장은 머리글 바로 아래 그룹 도형(top 5.4 cm, h 2.3~3.9 cm)에 평서문, Ⅰ장은 큰따옴표 인용문(16pt 굵게, 파랑)으로 핵심 메시지.
- **RFP 요구사항 ID 직접 인용**: "주요 수행 요구사항" 카드에 `SFR-001 / (요구 명칭)`, `SCR-003, SCR-004 / (요구 명칭)`처럼 RFP ID와 요구 명칭을 짝지어 배치하고 아래에 세부 기능 글머리. (Phase 11의 `rfp_requirement_id`와 바로 연결된다.)
- **대응 구조 반복**: "고객의 핵심 요구사항 ↔ 요구사항 해결을 위한 필요사항" 2열 비교, "핵심 성공요소 1·2·3" 번호 박스, "N대 전략에 따른 M개 과제", 단계 흐름(분석 → 설계 → 개발) 화살표 박스.
- **표 유형**: `구분 | 위험요소 | 대처 방안`, `단계 | 산출물명 | 제출시기 | 제출방법`, `구분 | 주요기능 | 구성 | 비고`, `구분 | 세부규격`, `용역명 | 발주처`(적용사례), `영역 | 활동내역 | 담당자`, 간트(A3).
- **본문 밀도**: 본문 고딕 8.5~10pt, 제목·강조는 같은 계열 굵은 글꼴. 슬라이드당 도형 10~48개(그룹·그림·도형 혼합). 발표자 노트 없음.
- **RFP 작성 조건 반영**: A4 세로, 장별 쪽번호, 한글 작성(영문 약어표), 100쪽 이내 권고 — RFP "제안서 작성지침" 절의 조건이 그대로 서식에 반영됨.

## 3. 프로그램에 반영한 일반화 (Phase 12)

고객사마다 템플릿이 다르므로 **샘플의 값을 하드코딩하지 않고**, 제안 때마다 업로드한 템플릿 PPTX에서 코드가 프로파일을 읽어 쓴다.

| 샘플에서 본 것 | 일반화 | 구현 |
|---|---|---|
| A4 세로, 장별 레이아웃, 마스터 고정 요소 | 템플릿 파일의 마스터·레이아웃을 그대로 쓰고 기존 슬라이드만 제거 | `generators/pptx/template.py` `TemplateDeckBuilder` |
| 머리글 2단 좌표·글꼴 | 슬라이드의 절반 이상에서 같은 위치에 반복되는 상단 텍스트 상자를 머리글로 인식 | `profile_template()` 머리글 탐지 |
| 리드 메시지 위치 | 머리글 아래 넓은 도형이 반복되면 리드 상자로, 없으면 기본 위치 | `TemplateProfile.lead` |
| 장 표지 | 로마숫자·CHAPTER 라벨이 있는 슬라이드의 레이아웃을 장 표지 레이아웃으로 | `TemplateProfile.chapter_layout` |
| 장·절·소절 번호, "(계속)" | 번호는 코드가 매기고 이어지는 슬라이드에 "(계속)" | `TemplateDeckBuilder.begin_chapter/begin_section` |
| 쪽번호 `Ⅰ - ‹#›` | 레이아웃의 쪽번호 필드를 그대로 사용 | 레이아웃 선택 `layout_for_chapter` |
| RFP 지정 목차 준수 | RFP 프로파일의 목차 트리(장/절/작성방법)로 장·절을 만들고 내용 없는 절은 "사람 작성 필요" 표시 | `outline.plan_chapters`, `rfp_profile.proposal_toc_tree` |
| RFP ID 카드, 리드 문장, 표 | 제안 문안 스키마에 `chapter/section/number/lead_message/table_*/requirement_ids/footnotes` | `agents/schemas.ProposalSection`, 프롬프트 |
| 글꼴·크기·표 머리글 색 | 템플릿 본문에서 가장 많이 쓰인 글꼴·크기, 표 머리글 채움색을 추출 | `TemplateProfile.fonts/table_style` |
| 서식 준수 검사 | 생성 PPT의 크기·머리글 위치·장 순서·글꼴을 템플릿과 대조 | 통합 QA `QA-FILE-11` |

A3 가로 별지(세부 일정)는 한 PPT 파일 안에 다른 용지 크기를 섞을 수 없어 이번 범위에서 제외했다(일정은 A4 본문에 간트 이미지·표로 들어간다).

## 4. 발표용 제안서 샘플 분석 (2026-10-15 추가)

대상: 고객 실과제 발표용 제안서 샘플 1종 (30.3 × 21.6 cm 가로, 35장, 발표자 노트 없음, 레이아웃 11종; 저장소 밖, 커밋·공개 금지).

### 4.1 구조

| 순서 | 슬라이드 | 구성 |
|---|---|---|
| 1 | 표지 | 사업명(큰 제목) · "제안발표회" · 일자 |
| 2 | 제안발표에 앞서 | 사업 필요성 — 사업 범위 3개 영역을 카드로, 각 카드에 한 줄 효과 |
| 3 | CONTENTS | Ⅰ~Ⅳ 로마숫자 카드 + 장 이름 (사업의 이해 / 사업수행방안 / 성능 및 품질 / 사업 관리 및 지원 / Ⅴ 특별 제안) |
| 4, 12, 20, 26, 33 | CHAPTER 구분 | "CHAPTER" 라벨 · 로마숫자(큰 글꼴) · 장 이름 · 절 번호(01~06)와 절 제목 목록 |
| 5~11, 13~19, 21~25, 27~32, 34 | 본문 | 머리글 1단 `NN/ 절 제목`(top 1.1 cm, 16~25pt) → 큰따옴표 리드 메시지(top 3.5~4.2 cm, 1~2문장) → 본문 도식 |
| 35 | 마무리 | 사업명 · 다짐 문구 |

### 4.2 본문 작성 방식 (요구사항 대응)

- **절마다 리드 메시지 1문장** 후 **도식 중심**: 번호 카드(01/02/03), 2열 비교("현황 및 이슈 ↔ 시스템 구성 방안", "현황 → 개선 수행 방안"), 단계 흐름(화살표·선 7~24개), 목표시스템 구성도(그룹·그림 수십 개), 시간 축(M, M+1 …), 조직도, 품질 절차 흐름. 표는 35장 중 7개뿐이며 글머리 목록보다 도형·연결선이 압도적(자동 도형 949, 자유형 234, 선 204, 그림 219).
- **요구사항 → 현황/이슈 → 방안 → 주요 기능** 순으로 설명하고, 구현 수단을 **구체적 제품·사양**(솔루션 제품명·버전, 서버 모델, 처리 범위·지원 포맷)으로 제시한다. 즉 구현 가능성 검토(조사)가 선행된 내용만 발표한다.
- 비기능(성능·시험·인터페이스·소스 품질·품질보증)은 Ⅲ장에서 **수치 목표**(응답 시간 초 단위, 자원 사용률 %)와 **절차 흐름**으로 제시.
- RFP 요구사항 ID는 발표용에서 인용하지 않는다(제출용과 차이). 본문 고딕 9~11pt, 머리글 16~25pt, 로마숫자 80pt.

### 4.3 프로그램 반영 (Phase 13)

| 샘플에서 본 것 | 일반화 | 구현 |
|---|---|---|
| 도형·연결선 중심의 도식 | 그림(PNG) 삽입 대신 **편집 가능한 도형·연결선·텍스트**로 그린다 — 카드, 단계 흐름, 2열 비교, 데이터 흐름, 호출 절차, 화면 설계(와이어프레임), 구성도, 일정 축, 공수 막대, 핵심 수치 | `generators/pptx/shapes.py` |
| 절마다 리드 메시지 + 도식 + 요점 | 제안 문안 스키마에 `visual`(종류·항목·연결) 추가, 에이전트가 지정하면 코드가 그린다. 지정이 없으면 데이터로 기본 도식 | `agents/schemas.VisualSpec`, `decks.py` |
| 구체 제품·사양으로 구현 방안 제시 | 제안 문안 작성 전 기술 조사(웹 검색) 선행을 강제하고, 구현 방안은 조사 근거가 있는 것만, 근거 없으면 "조사 필요" 표기. 조사 결과로 요구사항 구현 방안을 채움 | `StepRunner.run_proposal_writing`, `ResearchService.run`, QA-TECH-07 |
| 표지 → 필요성 → CONTENTS → CHAPTER → 본문 → 마무리 | 발표용 덱 구조를 이 순서로 재구성, 장 뼈대는 발표용 템플릿 장 → RFP 목차 → 기본 4장 | `decks.build_presentation_deck` |
| 머리글 1단 `NN/ 제목`, "(1/2)" 분할 | 템플릿 프로파일이 머리글 단수·번호 표기 방식·분할 표기를 읽어 그대로 쓴다 | `template.py` |
| 모든 요소 편집 가능 | 생성 PPT에 그림 도형이 없어야 함(QA-FILE-12), Excel·표·선·상자는 모두 네이티브 개체 | `validation` |
