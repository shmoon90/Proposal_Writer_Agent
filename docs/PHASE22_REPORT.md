# Phase 22 보고서 — 요구사항 묶음별 구현 방안 소절·장표 구성 개선·QA-CON-12 (2026-10-16)

사용자 검토 의견("제안서의 구현 방안이 부실하고 정의서 구현방안이 제안서에 반영되지 않음", "세로형 박스 일색·빈칸 많음", "요구사항은 내용상 필요하면 묶어서 작성")과 같은 RFP의 실제 제안서 샘플(Ⅲ장, 저장소 밖)의 구성·작성 수준을 반영했다. 샘플 내용은 참고만 했고 저장소에 두지 않았다.

## 1. 원인 (검토 결과)

- 덱 생성기는 제안 문안 소절 중심이라 정의서의 요구사항별 구현방안(approach_writer 결과)을 표 셀 60자, 발표용 2열 60자로만 썼고, 요구사항별 전문을 나열하는 '구현 방안' 슬라이드는 문안 에이전트가 글머리를 준 경우 건너뛰는 대체 경로였다. 문안 에이전트에게는 구현방안이 100~120자로 잘려 전달됐고, 요구사항마다 소절을 쓰라는 규칙도 없었다. QA는 요구사항 ID 언급만 보고 구현방안 **내용** 반영은 검사하지 않았다.
- 도식은 영역 전체를 세로로 채우는 상자(카드·띠·2열)라 내용이 적으면 빈 상자가 커졌고, 소절마다 도식·기술 상세·표가 각각 한 장이라 장표당 내용 밀도가 낮았다.

## 4. 남은 한계

- 블록 높이는 글꼴·폭 기반 추정이라 장 하단에 여백이 남거나(표 행이 다음 장으로 넘어감) 드물게 빠듯할 수 있다. 샘플처럼 화면 캡처·아이콘·사진을 섞은 밀도는 그림 정책상(정보성 이미지 금지) 내지 않는다.
- 묶음 소절은 정의서 구현방안을 그대로 싣는다. 구현방안 자체의 깊이(기술 선택·대안·절차)는 `approach_writer`/실제 모델 품질에 달려 있다.
- 블록 도식의 사용자·연계 대상은 요구사항 이름·방안의 키워드 추정이다.
